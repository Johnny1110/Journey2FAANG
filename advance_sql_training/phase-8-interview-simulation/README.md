## 這一章為什麼不一樣

Phase 1~7 的題目都是「有正確答案，看你寫不寫得出來」。

**真實面試不是這樣。** 面試官會丟一句「幫我算一下活躍用戶數」，然後看你：

- 會不會**問清楚定義**（還是直接開始寫）
- 會不會**主動提出邊界**（NULL、重複、時區、測試帳號）
- 會不會**說明取捨**（為什麼選這個寫法而不是那個）
- 寫完會不會**自己找 bug**

**這一章的每一題都是故意寫得模糊的。** 照字面實作的人會拿低分 —— 即使 SQL 完全正確。

## 評分標準

| 面向 | 佔比 | 說明 |
|------|------|------|
| **需求釐清** | 30% | 你問了什麼問題？問得夠具體嗎？ |
| **SQL 正確性** | 30% | 在你自己定義的假設下，SQL 對嗎？ |
| **邊界與髒資料** | 20% | NULL、重複、缺漏、測試帳號、時區 |
| **效能與取捨** | 20% | 資料量大十倍會怎樣？你的方案為什麼比替代方案好？ |

<br>

> ⚠️ **硬性規定：`answer.sql` 必須以「我會先問面試官這幾個問題」開頭。**
>
> 直接寫 SQL 的一律**扣 3 分**，即使 SQL 完美。
>
> 而且問題要用**具體情境**問，不能用抽象規則問 ——
> ❌「請問活躍的定義是什麼？」
> ✅「一個使用者今天開了 App 但什麼都沒點，他算活躍嗎？」

## 建議的作答結構

```sql
-- ============================================================
-- 1. 我會先問面試官的問題
-- ============================================================
-- Q1: （具體情境）...
-- Q2: ...
-- Q3: ...

-- ============================================================
-- 2. 我的假設（在對方回答之前，我先這樣假設並說明）
-- ============================================================
-- 假設 A: ...  理由: ...

-- ============================================================
-- 3. SQL
-- ============================================================
...

-- ============================================================
-- 4. 邊界情況
-- ============================================================
-- 我處理了: ...
-- 我沒處理但知道存在: ...

-- ============================================================
-- 5. 效能與取捨
-- ============================================================
-- 目前資料量下: ...
-- 資料量 x1000 時: ...
-- 替代方案與為什麼我不選它: ...
```

**這個結構本身就是答案的一部分。** 面試現場你講出來的東西，就照這個順序。
