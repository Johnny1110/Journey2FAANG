## Part A — 核心模式

### A1 — 先手算

**不要碰鍵盤。** 拿紙筆，對 user 4 的日期（3/10, 3/11, 3/12, 3/13, 3/14, 3/20）做這件事：

1. 依日期排序，標上序號 1, 2, 3, 4, 5, 6
2. 算出「日期 − 序號」

你會看到什麼？**為什麼連續的那 5 天算出來是同一個值？**

用文字寫出你的觀察 —— 這一句話就是整個 Gaps and Islands 的原理。

### A2 — 寫出來

用 A1 的洞察寫出查詢，輸出每個使用者的最長連續登入天數。

PostgreSQL 提示：
- `TIMESTAMP` 轉日期用 `login_at::date`
- `date - integer` 得到 `date`（`ROW_NUMBER()` 回傳 `bigint`，需要 `::int` 轉型）

### A3 — 列出所有區段

把查詢擴充成輸出**每一段連續區間**的明細：

```
 user_id |  from_day  |   to_day   | len
---------+------------+------------+-----
       1 | 2026-01-01 | 2026-01-03 |   3
       1 | 2026-01-05 | 2026-01-06 |   2
       2 | 2026-01-01 | 2026-01-05 |   5
       3 | 2026-02-14 | 2026-02-14 |   1
       4 | 2026-03-10 | 2026-03-14 |   5
       4 | 2026-03-20 | 2026-03-20 |   1
```

## Part B — user 2 的陷阱

### B1 — 先寫錯的版本

**直接**對 `logins` 表套用 A2 的公式（不做任何去重），跑出來：

```
 user_id | longest_streak
---------+----------------
       1 |              3      ← 對
       2 |              3      ← 錯！應該是 5
       3 |              1      ← 對
       4 |              5      ← 對
```

**四個使用者裡三個是對的。** 又是那個熟悉的模式 —— 這種 bug 上線後沒人會發現。

### B2 — 診斷

user 2 在 1/2 和 1/3 各登入了兩次。

**把 user 2 的每一行列出來**，標上 `login_at::date`、`ROW_NUMBER()`、以及 `date - rn`：

| login_at | date | rn | date − rn |
|----------|------|----|-----------|
| 01-01 08:00 | ? | 1 | ? |
| 01-02 09:00 | ? | 2 | ? |
| 01-02 14:00 | ? | 3 | ? |
| … | | | |

回答：
- 重複的日期讓 `date − rn` 發生什麼事？
- 為什麼會把一段連續的 5 天**切成兩段**？
- **為什麼 user 1、3、4 不受影響？**（它們的資料有什麼特徵？）

### B3 — 修好它

加上去重。寫出正確版本，確認 user 2 得到 5。

回答：
- `SELECT DISTINCT user_id, login_at::date` 和 `GROUP BY user_id, login_at::date` 哪個好？有差嗎？
- 去重要放在**哪一層**？如果放在 `ROW_NUMBER()` 之後會怎樣？

### B4 — 通用教訓

**寫出這句結論**：Gaps and Islands 的序號差值法，前提是 `______`。任何時候只要 `ORDER BY` 的欄位可能重複，就必須先 `______`。

## Part C — 變形

同一個模式，換三種問法。**每一題都只需要小改 Part A 的查詢。**

### C1 — 目前的連續天數

不是「歷史最長」，是「**截至今天為止還在進行中的連續天數**」（連續登入獎勵實際需要的是這個）。

假設今天是 `2026-03-20`。user 4 的答案是多少？user 1 呢？

### C2 — 連續交易日

如果「連續」的定義**排除週末**（只算工作日），公式要怎麼改？

（提示：不要改公式，改**序號的來源** —— 想想 [Phase 1-07](../../phase-1-join-dark-side/07-the-report-with-missing-rows) 的骨架心法）

### C3 — 連續的狀態值

換一張表：伺服器每分鐘回報一次狀態（`up` / `down`）。找出**每一段連續 `down` 的區間**及其長度。

這是 SRE 算 SLA 停機時間的標準查詢。用同樣的模式寫出來 —— 但序號要怎麼取？

（提示：`ROW_NUMBER() OVER (ORDER BY t) - ROW_NUMBER() OVER (PARTITION BY status ORDER BY t)` —— 想想為什麼這個差值在同狀態連續段內是常數）

## Hints

<details>
<summary>Hint 1 — 為什麼 date − rn 是常數</summary>

user 4 的日期與序號：

| day | rn | day − rn |
|-----|----|----------|
| 03-10 | 1 | **03-09** |
| 03-11 | 2 | **03-09** |
| 03-12 | 3 | **03-09** |
| 03-13 | 4 | **03-09** |
| 03-14 | 5 | **03-09** |
| 03-20 | 6 | 03-14 |

**原理**：連續的日期每次 +1，序號也每次 +1，**兩者同步增加，差值不變**。

一旦日期跳過（03-14 → 03-20 跳了 6 天），日期增加 6 但序號只增加 1 → 差值變大 → **新的島**。

所以 `day - rn` 就是**島的 ID**。`GROUP BY user_id, (day - rn)` 就把每一段連續區間分好組了。

**這個值本身沒有意義**（03-09 不代表什麼），它只是一個「同一段內相同、跨段不同」的標籤。

</details>

<details>
<summary>Hint 2 — 骨架</summary>

```sql
WITH days AS (
    SELECT DISTINCT user_id, login_at::date AS day     -- ← 去重，Part B 的關鍵
    FROM logins
),
islands AS (
    SELECT user_id, day,
           day - (ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY day))::int AS grp
    FROM days
),
streaks AS (
    SELECT user_id, grp, COUNT(*) AS len,
           MIN(day) AS from_day, MAX(day) AS to_day
    FROM islands
    GROUP BY user_id, grp
)
SELECT user_id, MAX(len) AS longest_streak
FROM streaks
GROUP BY user_id
ORDER BY user_id;
```

三層 CTE，每一層一件事：**去重 → 標島 → 彙總**。

面試時就這樣寫 —— 分層命名讓考官一眼看懂你的思路，比擠成一個巢狀子查詢好太多。

</details>

<details>
<summary>Hint 3 — user 2 為什麼被切成兩段</summary>

| login_at | day | rn | day − rn |
|----------|-----|----|----------|
| 01-01 08:00 | 01-01 | 1 | **2025-12-31** |
| 01-02 09:00 | 01-02 | 2 | **2025-12-31** |
| 01-02 14:00 | 01-02 | 3 | 2025-12-30 |
| 01-03 08:00 | 01-03 | 4 | 2025-12-30 |
| 01-03 21:00 | 01-03 | 5 | 2025-12-29 |
| 01-04 10:00 | 01-04 | 6 | 2025-12-29 |
| 01-05 10:00 | 01-05 | 7 | 2025-12-29 |

三個島：`{2 行}`、`{2 行}`、`{3 行}` → 最大值 **3**。

**重複的日期讓序號多跳了一格，但日期沒動** → 差值變小 → 假的斷點。

user 1、3、4 沒有重複日期，所以碰巧正確。**這就是為什麼測資一定要包含重複值** —— 不然你永遠測不出這個 bug。

</details>

<details>
<summary>Hint 4 — C3 的雙 ROW_NUMBER 技巧</summary>

```sql
ROW_NUMBER() OVER (ORDER BY t)                        -- 全域序號
- ROW_NUMBER() OVER (PARTITION BY status ORDER BY t)  -- 同狀態內的序號
```

在一段**連續同狀態**的區間內，兩個序號都是每次 +1，**差值不變**。
一旦狀態切換，全域序號繼續走但該狀態的序號重新接續 → 差值改變 → 新的島。

這叫 **Tabibitosan 法**（日本人取的名字），是 Gaps and Islands 的第二大變形。

**Part A 的 `day - rn` 和這裡的 `rn1 - rn2` 是同一個原理**：找一個「在段內同步變化、跨段失步」的量，用它當島 ID。

</details>
